# S3: Integer & Rounding Logic

- **SWC:** SWC-101 (integer overflow and underflow)
- **Severity:** high
- **Real-world:** BEC Token BatchOverflow (2018)

## The Vulnerability

`VulnerableToken` has two arithmetic defects.

### 1. Unchecked subtraction

```solidity
// VulnerableToken.transfer()
unchecked {
    balanceOf[msg.sender] -= amount;   // wraps on underflow
}
balanceOf[to] += amount;
```

Putting the subtraction inside `unchecked` tells the compiler to skip the
overflow check. If `amount` is larger than the sender's balance, the balance
wraps around to `2**256 - amount` instead of reverting. The attacker transfers
one token more than it owns and is instantly credited with `type(uint256).max`
tokens. Because `to` is also credited, the sum of all balances now exceeds
`totalSupply` — the token's core accounting invariant is broken.

### 2. Divide before multiply

```solidity
// VulnerableToken.pendingReward()
return (rewardPool / totalSupply) * balanceOf[account];
```

Solidity integer division truncates. Dividing the pool by the supply first
throws away the remainder, and multiplying that truncated quotient by the
member's balance often yields zero. With `rewardPool = 3`, `totalSupply = 10`
and a member holding `6`, the correct share is `(3 * 6) / 10 = 1`, but the
vulnerable formula computes `(3 / 10) * 6 = 0`. Members are silently underpaid
(or, with an inflated balance from bug 1, wildly overpaid).

## The Fix

`SecureToken` uses checked arithmetic and the correct operation order.

```solidity
// transfer: Solidity 0.8 checked math reverts with Panic(0x11) on underflow.
balanceOf[msg.sender] -= amount;
balanceOf[to] += amount;
```

```solidity
// pendingReward: multiply before dividing to keep precision.
return (rewardPool * balanceOf[account]) / totalSupply;
```

Now an over-transfer reverts, the sum of balances can never exceed
`totalSupply`, and each member's reward is computed with full precision before
the single, unavoidable truncation at the end.

## Why this matters

The 2018 BatchOverflow incident froze trading of several ERC20 tokens after a
`batchTransfer` multiplied user-supplied amounts without an overflow check,
minting an astronomically large balance for the attacker. The same class of bug
applies to underflow. Ordering bugs are subtler: they do not crash anything,
they just quietly pay the wrong amount, which is why they survive testing.

## Exploit walkthrough (lab)

1. The attacker holds nothing.
2. It calls `transfer(recipient, 1)` — a token it does not own.
3. **Vulnerable:** the subtraction wraps. The attacker's balance becomes
   `type(uint256).max` out of an empty balance, `profit()` reports the same, and
   a single balance now exceeds the entire `totalSupply`. The separate reward
   bug shows a member receiving `0` instead of the correct `1`.
4. **Secure:** the same transfer reverts with a checked-arithmetic panic; the
   balance stays `0` and `profit()` is `0`.
