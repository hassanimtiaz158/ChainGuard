# S6: Front-Running (Public Reveal and Unbounded Slippage)

- **SWC:** SWC-114 (transaction order dependence)
- **Severity:** high
- **Real-world:** DEX front-running / sandwich attacks (2017-)

## The Vulnerability

Two flavours of the same bug are shown here.

**1. Public reveal.** `VulnerableQuiz` pays the first person to submit the
correct answer, and it compares that answer in the clear:

```solidity
// VulnerableQuiz.submitAnswer()
if (keccak256(bytes(answer)) != answerHash) {
    revert WrongAnswer();
}
```

The winning answer is not secret while it is pending: it travels through the
mempool as calldata before it is mined. Anyone watching pending transactions
can read it, copy it, and resubmit it with a higher priority fee so their
transaction is ordered first.

**2. Unbounded slippage.** `VulnerableSwap` forwards a trade to the constant
product pool without stating a minimum output or an expiry:

```solidity
// VulnerableSwap.swapExactInput()
amountOut = amm.swap(_token0In ? amountIn : 0, _token0In ? 0 : amountIn, 0, msg.sender);
```

The `0` is `minAmountOut`. Whatever price the pool is at when the trade lands
is the price the caller gets.

## The Attack

Both attacks are ordering attacks; on the lab chain the order is fixed
explicitly rather than left to chance.

**Quiz.** The attacker watches the mempool, sees `submitAnswer("satoshi")`,
and lands the same call first:

```solidity
// Attacker.attack()
quiz.submitAnswer(answer);
```

The vulnerable quiz is now `solved`, the prize has been paid to the attacker,
and the honest solver's transaction reverts with `AlreadySolved`.

**Swap.** A sandwich bot buys the victim's output token first
(`amm.swap(500e18, 0, ...)`), pushing its price up. The victim's unprotected
trade then settles at the worse price. In the test the victim receives under
half of the fair quote — well past the 20% slippage bound.

## The Fix

**Commit-reveal.** `SecureQuiz` splits the answer into two transactions:

```solidity
// SecureQuiz.reveal()
if (keccak256(abi.encode(answer, salt, msg.sender)) != commitment) {
    revert BadReveal();
}
```

- The solver first calls `commit(keccak256(abi.encode(answer, salt, solver)))`.
  Only a hash is on-chain, so a front-runner learns nothing about the answer.
- After `REVEAL_DELAY` blocks the solver calls `reveal(answer, salt)`. The
  commitment is bound to `msg.sender`, so copying the visible commitment and
  revealing from another account fails with `BadReveal`, even though the copied
  value is byte-for-byte identical.
- Plaintext submission is disabled entirely (`PlaintextSubmissionDisabled`), so
  the S6 entry point is gone.

**Slippage parameters.** `SecureSwap` takes a `minOut` and a `deadline`:

```solidity
// SecureSwap.swapExactInput()
if (block.timestamp > deadline) {
    revert DeadlineExpired();
}
amountOut = amm.swap(_token0In ? amountIn : 0, _token0In ? 0 : amountIn, minOut, msg.sender);
```

If the price moved below `minOut`, the AMM reverts with `InsufficientOutput`
instead of filling; if the trade is stale, it reverts with `DeadlineExpired`.

## Why this matters

Any value that is revealed in a pending transaction can be taken by whoever
pays enough to be ordered first. Commit-reveal removes the information leak;
it does not hide *that* someone is about to act, only *what* they are about to
do, which is enough to make copying useless. On the AMM side, a caller has no
control over the block their transaction lands in, so the contract must be
given the terms the caller is willing to accept — a floor on output and an
expiry. "Send whatever and hope" is an invitation to be sandwiched.

## Exploit walkthrough (lab)

- The quiz holds a `5 ETH` prize.
- The attacker copies the plaintext answer from the pending solver transaction
  and submits it first, taking the full prize.
- For the swap, the pool starts at `1000 / 1000`. The bot buys `332` units of
  the output token first; the victim's `100`-unit trade then returns roughly
  `41` instead of the fair `91` — a loss of more than half.

Against the secure quiz the attacker's plaintext submission reverts and the
prize stays put. Against the secure swap, the same front-run makes the victim's
transaction revert with `InsufficientOutput`, so the victim keeps their tokens
and can retry at a price they accept.
