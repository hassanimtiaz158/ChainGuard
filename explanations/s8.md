# S8: Unchecked External Call

- **SWC:** SWC-104 (unchecked call return value)
- **Severity:** high
- **Real-world:** Unchecked ERC20 transfer returns (Tether-style tokens)

## The Vulnerability

`VulnerablePayout` moves value and then updates its ledger without ever looking
at whether the move succeeded.

```solidity
// VulnerablePayout.payout()  — ETH side
to.call{value: amount}("");        // return value discarded
totalEthPaid += amount;            // ledger advanced regardless
```

```solidity
// VulnerablePayout.payoutToken()  — token side
token.transfer(to, amount);        // returns false on failure; ignored
totalTokenPaid += amount;          // ledger advanced regardless
```

Two things make this dangerous in practice:

1. **Low-level `call` never reverts on its own.** It returns `false`. If the
   recipient is a contract that rejects ETH, or the transfer runs out of gas,
   the failure is invisible unless the caller checks the boolean.
2. **Non-standard ERC20s return `false` instead of reverting.** `USDT` and other
   pre-convention tokens do exactly this. Code that assumes `transfer` reverts
   on failure will happily record a payment that never happened.

The result is a payout desk whose books no longer match reality: `totalEthPaid`
and `totalTokenPaid` claim money left the building when it did not.

## The Fix

`SecurePayout` enforces both transfer results.

```solidity
// ETH: check the boolean and revert on failure.
totalEthPaid += amount;
emit EthPaid(to, amount);
(bool success,) = to.call{value: amount}("");
if (!success) revert TransferFailed();
```

```solidity
// Token: SafeERC20 converts a false return into a revert.
totalTokenPaid += amount;
emit TokenPaid(to, amount);
token.safeTransfer(to, amount);
```

`SafeERC20.safeTransfer` accepts tokens that return no data *and* tokens that
return a boolean; it reverts with `SafeERC20FailedOperation(token)` whenever the
call fails or returns `false`. A failed payment can no longer be recorded as a
successful one.

## Why this matters

Not every vulnerability is a heist. S8 is a **correctness** bug: the contract
silently lies about what it has paid. Downstream, that breaks accounting,
reconciliation and any logic that trusts the payout counter. The cost is trust,
not a single drained balance — which is exactly why it is easy to miss in
review.

## Exploit walkthrough (lab)

1. The desk is funded with 10 ETH and 10 tokens.
2. A recipient that rejects ETH asks the desk to pay it everything it holds.
3. **Vulnerable:** the ETH transfer fails, but `totalEthPaid` jumps to 10 ETH.
   The desk still holds all 10 ETH, yet reports it paid them out. The recipient
   received nothing — the adversary's `profit()` is 0 by design.
4. **Secure:** the failed transfer reverts the whole transaction. The ledger is
   left at 0 and the funds stay put.

The token case is identical, driven by `MockNonStandardERC20.setTransferFails`.
