# S1: Reentrancy (Checks-Effects-Interactions)

- **SWC:** SWC-107
- **Severity:** critical
- **Real-world:** The DAO (2016)

## The Vulnerability

`VulnerableVault.withdraw()` performs its interaction before its effect:

```solidity
// VulnerableVault.withdraw()
(bool success,) = msg.sender.call{value: amount}("");   // INTERACTION first
if (!success) revert TransferFailed();
balanceOf[msg.sender] = 0;                              // EFFECT second (too late)
```

When `msg.sender` is a contract, the ETH transfer hands control to that
contract's `receive()`. Because `balanceOf[msg.sender]` is still the original
value, the attacker can call `withdraw()` again from inside `receive()` and be
paid a second time. Each nested call repeats this until the vault is empty.

`Attacker.receive()` re-enters for as long as `address(vault).balance > 0`, so
the recursion terminates only when there is no ETH left to steal.

## The Fix

`SecureVault` applies two independent defenses:

1. **Checks-Effects-Interactions.** The ledger is zeroed *before* the external
   call, so a re-entrant `withdraw()` reads a balance of `0` and reverts with
   `InsufficientBalance`.
2. **OpenZeppelin `ReentrancyGuard`.** `withdraw()` is `nonReentrant`, so even
   if the ordering were wrong, a nested call reverts with
   `ReentrancyGuardReentrantCall`.

### Why the secure vault bubbles the revert

A naive fix writes:

```solidity
(bool success,) = msg.sender.call{value: amount}("");
if (!success) revert TransferFailed();
```

That low-level `call` **absorbs** the attacker's revert and replaces it with a
generic `TransferFailed()`. The attacker is still stopped, but the real reason
is hidden. `SecureVault` forwards the recipient's revert data instead, so the
guard's `ReentrancyGuardReentrantCall` surfaces to the caller. This is a
diagnostic improvement only — the transaction reverts either way.

## A note on the re-entry condition

The attacker gates re-entry on the **vault's ETH balance**, not on
`vault.balanceOf(attacker)`. This matters: with `balanceOf` as the gate, the CEI
fix alone would silently stop the recursion, and the `ReentrancyGuard` would
never actually be exercised. Gating on the vault's balance keeps the attacker
pressing until the money is gone, which is what makes the hardened vault
genuinely reach — and revert from — the guard.

## Exploit walkthrough (lab)

Starting state: the vault holds 10 ETH deposited by three victims; the attacker
holds a 1 ETH seed.

1. `attack()` deposits 1 ETH. Vault: 11 ETH, `balanceOf[attacker] = 1`.
2. `withdraw()` sends 1 ETH out, then hands control to `Attacker.receive()`.
3. `receive()` re-enters `withdraw()`. `balanceOf[attacker]` is still 1, so
   another 1 ETH goes out. This repeats.
4. The vault hits 0 ETH with `balanceOf[attacker]` still 1; the next `receive()`
   sees an empty vault and stops.
5. Net result: the vault holds 0 ETH (all three victims' funds are gone) and the
   attacker's profit is 10 ETH.

Against `SecureVault`, step 2 zeroes the ledger first, and the nested call is
refused by the guard. The whole transaction reverts, the victims' 10 ETH is
untouched, and the seed is returned to the attacker by the revert.

| Test | What it pins down |
|---|---|
| `test_exploit_succeeds_on_vulnerable` | Vault drains to 0; attacker profit equals the full 10 ETH |
| `test_exploit_fails_on_secure` | Reverts with `ReentrancyGuardReentrantCall` |

| `test_secure_vault_rejects_unsolicited_eth` | Direct ETH sends are refused, protecting the ledger |
| `test_revertWhen_attackingWithoutSeed` | The attack cannot start with no seed |
| `test_profitIsZeroBeforeAnyAttack` | `profit()` reports zero before any draining |
| `invariant_sumOfBalancesEqualsContractBalance` | Ledger total always equals real ETH held |

## Why this matters

Reentrancy is the canonical smart-contract vulnerability and the reason
"Checks-Effects-Interactions" is a standard code-review checklist item. Any
contract that sends ETH (or makes arbitrary external calls) to an address it
does not control must update its own state before handing over control, and
should layer a reentrancy guard on top.
