# S7: Signature Replay

- **SWC:** SWC-121 (missing protection against signature replay attacks)
- **Severity:** high
- **Real-world:** pre-EIP-712 airdrops and bridges

## The Vulnerability

`VulnerableClaim` is a voucher vault: an off-chain signer authorises payouts by
signing a message, and anyone holding the signature can present it to redeem.

The signature commits to `(to, amount)` and nothing else:

```solidity
// VulnerableClaim._verifyVoucher()
bytes32 digest = MessageHashUtils.toEthSignedMessageHash(keccak256(abi.encodePacked(to, amount)));
return ECDSA.recover(digest, signature) == signer;
```

`claim` accepts a `nonce`, but that nonce is only emitted — it is never part of
the signed digest and never recorded. There is no domain separator either, so
the signature is not tied to this contract or to the chain. A signature that
verifies once verifies forever, on every deployment, on every chain.

## The Attack

1. The attacker captures a valid voucher, for example by watching the mempool
   for an honest redemption.
2. It redeems it. The vault pays.
3. It redeems *the exact same signature* again. The vault pays again.

Repeating step 3 drains the vault. Against the lab's `5 ETH` vault and a
`1 ETH` voucher, the attacker takes `3 ETH` in the test before the vault runs
dry; nothing stops it from continuing until the balance is gone.

## The Fix

`SecureClaim` signs EIP-712 typed data and consumes a nonce:

```solidity
// SecureClaim.claim()
_useCheckedNonce(to, nonce);
if (!_verifyVoucher(to, amount, nonce, signature)) revert BadSignature();
```

```solidity
// SecureClaim.hashClaim()
return _hashTypedDataV4(keccak256(abi.encode(CLAIM_TYPEHASH, to, amount, nonce)));
```

Three things change:

- **Nonce.** Each recipient has a sequence from OpenZeppelin `Nonces`.
  `_useCheckedNonce(to, nonce)` requires the supplied nonce to equal the
  recipient's current one and then increments it, so a voucher is single-use.
  Replaying the signature reverts with `InvalidAccountNonce`.
- **Struct.** The signed struct is `Claim(address to, uint256 amount, uint256 nonce)`,
  so the nonce is covered by the signature. Nobody can swap it for a different
  value.
- **Domain separator.** `_hashTypedDataV4` mixes in the EIP-712 domain
  (name, version, **chain id**, **verifying contract**). A signature for one
  deployment or one chain is rejected everywhere else with `BadSignature`.

## Why this matters

A signature is a bearer instrument: whoever holds the bytes can present them.
If the signed payload does not identify *when* and *where* it is valid, then
validity is unbounded. Three fields make it bounded — a nonce (single use), the
chain id (one network) and the verifying contract address (one deployment).
EIP-712 packages all of this into the domain separator so implementations
cannot silently forget it. Note that the fix here tracks nonces per *recipient*;
other designs track them per signer or globally, but the invariant is the same:
each authorisation must be redeemable at most once.

## Exploit walkthrough (lab)

- The vault is funded with `5 ETH`.
- The issuer signs `Claim(to = attacker, amount = 1 ETH, nonce = 0)`.
- The attacker redeems it, then redeems it again — the vulnerable vault pays
  `2 ETH` and would keep paying.

Against the secure vault the first redemption consumes nonce `0`. The second
submission of the identical signature reverts with
`InvalidAccountNonce(attacker, 1)`, the vault holds `4 ETH` and the attacker has
gained exactly `1 ETH`.

## Tests

| Test | What it pins down |
|---|---|
| `test_replay_succeeds_on_vulnerable` | The same signature is redeemed repeatedly and drains the vault |
| `test_replay_fails_on_secure` | The replay reverts with `InvalidAccountNonce`; only one payout |
| `test_secure_signatureIsBoundToContract` | A signature for one deployment is invalid on another |
| `test_secure_noncesArePerRecipient` | One claimant cannot consume another's nonce sequence |
| `test_revertWhen_badSignatureOnVulnerable` | A digest that does not match the recipient is rejected |
| `test_revertWhen_badSignatureOnSecure` | Same, for the typed-data digest |
| `test_revertWhen_secureClaimingToZeroRecipient` | Zero-address payouts are rejected |
| `test_revertWhen_vulnerableClaimingToZeroRecipient` | Same, for the vulnerable vault |
| `test_revertWhen_vulnerableRejectsZeroSigner` | The constructor rejects a zero signer |
| `test_revertWhen_secureRejectsZeroSigner` | Same, for the secure vault |
| `test_revertWhen_vulnerablePayoutToRejectingRecipientFails` | A recipient that rejects ETH is handled |
| `test_revertWhen_securePayoutToRejectingRecipientFails` | Same, for the secure vault |
| `test_revertWhen_attackerRejectsZeroTarget` | The attacker rejects a zero target |
| `test_attackerCanSweepReplayedFunds` | The replayed funds can be extracted |
| `test_revertWhen_sweepToRejectingOwnerFails` | A rejecting sweep target is handled |
| `test_signersAreExposed` | Both vaults expose the authorised signer |
